- **Phase 11 (planned): project types as data.** A project type becomes one YAML file, still one level: levels, checks, gates, judges (questions and what a "no" means, built into Jev specs) and teams. Teams are one of four mechanisms kept in code (producer, probing reviewer, quoting reviewer, planner) plus data (name, instructions, finding kind, evidence). A project names its preset by name or path, so new types need no code, and the fixed list of domains goes. Due: when the user wants a third concrete project type, which then drives and validates the format (decided with the user, 2026-10-04, under the scope rule: generalize from real cases, not imagined ones). Refinements: presets get sub-labels (`software/python`, `software/node`, `document/markdown`), plain files in a folder, and users can add their own. Nesting is single inheritance only (`extends:` one parent, chains allowed), with one merge rule (a child's key replaces the parent's; teams matched by name; lists never merged item by item), and `agentswarm config` shows the resolved result and which file each setting came from. Binary formats such as Word are outputs, not working formats: `document/word` would extend `document/markdown` with an export step (e.g. pandoc), since the file tools, git diffs and quoting reviewers all need text.
- **Models choosing tasks, when capacity is the limit (the user's question, 2026-10-07).** Today each task's call picks a model (the router), which is right while capacity is elastic (hosted APIs). With fixed capacity (one local model loaded at a time, swaps costing seconds to minutes) the other view fits: a free model pulls the hardest waiting task it is still predicted good enough for, and tasks of one model are batched to avoid swaps. More generally (the user: a machine with 150-200 GB would hold several models at once): any fixed fleet, whether one big machine, rented GPUs or rate-limited APIs, has limited throughput; on Apple silicon concurrent models share memory bandwidth, so swaps disappear but contention doesn't. Both views are one assignment problem: the router's predicted success per (task, model) stays the input; a capacity-aware scheduler keeps each loaded model busy on the hardest work it is good enough for and sends the rest elsewhere. Before buying hardware, probe the open models it would run through a pay-per-token API (the compute item below). Design sketch (the user's, 2026-10-07): each model declares its capacity in the config (1 at a time locally, unlimited or a rate limit when hosted); each task carries its demand (the models predicted good enough, and a priority); a free model pulls from its own view of the board's open tasks, first those only it or a scarcer model can do, then anything it is good enough for. Views over the board, not real queues. With unlimited capacity this reduces to today's router (cheapest good-enough model per task), so one mechanism serves every user's setup. The board already has teams pulling work (claims), so it would be a scheduling policy, not a new architecture. Due: when local-model runs show measurable idle GPU time or swap time.
- **Compact builders' history with Jev (from a Jev use-case article the user shared, 2026-10-07).** A builder resends its whole conversation on every step: CommonMark worklist items used 2-4 million input tokens each, almost all of it old tool output. A reported Claude Code plugin (fast-jev-compaction) scores every tool call and result at compaction time, drops or shortens stale ones and keeps the rest verbatim (claimed: about 1M tokens to 90K in a second). Prompt caching already cuts the price of resent input by 90%, so the gain is speed and context room more than money. Due: stage 3 (dynamics and cost), or earlier if builders run out of context.
- **Post-mortems that make the next run cheaper (the user's idea, 2026-10-08).** (1) A waste report from a finished project's board, free: spend on items that were thrown away or escalated, repairs that didn't help, loops and capped runs, per model and kind of section; it turns a run into settings (step caps, tries, starting models). (2) Replay: every merged step is a solved task with its starting commit and its checks, so a finished project becomes a benchmark; cheaper models replay its steps offline and their outcomes go to the routing ledger at the step's real difficulty (as SWE-bench mines merged pull requests, and SWE-Gym and SWE-smith build task suites from repository histories). Due: the waste report when a stage-1 project finishes or stalls for good; replay once routing is in real use and there are many merged steps.
- **More compute than 24 GB of local memory (the user, 2026-10-06).** First choice, least effort: pay-per-token APIs for open models (OpenRouter, Together, Fireworks and similar): no GPUs, no downloads, many models, mostly OpenAI-compatible, so a model is one config line. Rented GPUs only for models no API serves, or for fine-tuning; then persistent storage (for example RunPod network volumes) so weights aren't downloaded again and no particular machine has to be rented. The user has a vast.ai account, but found re-downloading models and being tied to one machine awkward. Due: when a local model is too slow or too small for an experiment. Check current prices and model lists then.

| Many generators, compared: a loop that spawns several independent implementations of one spec and validates them by agreement (the user, 2026-10-11) | Parked | Established practice: AlphaCode (2022) clusters generated programs by their behaviour on generated inputs and picks from the largest clusters; CodeT (2022) ranks code by agreement with generated tests; self-consistency in reasoning. Design for AgentSwarm: K builder teams on different models and prompts write the same spec on separate branches; an input generator (fuzzer or agent) makes inputs without answers; a differential-tester team runs every version, groups them by behaviour, and posts each disagreement as a finding; a judge, a known-answer example or a person settles it, and the settled case becomes a new labeled test (active learning); losing versions are repaired against it under the ratchet. The weak point is correlated errors: independently written versions fail on the same hard inputs (Knight and Leveson, 1986), likely more so with similar models, so diversity must be built in (model families, prompts, algorithms), a majority is a hypothesis, and a disagreement is the stronger signal. Costs K times the generation, so only where test suites are missing. Trigger: a problem without a labeled test suite (stage 2 or the document projects). First step then: a few-dollar measurement on TOML and CommonMark, where answers are known, of how often a majority of a few versions is right on held-out tests and how often disagreements point at real bugs |
| A self-supervised project (the user, 2026-10-12: "fun, but possibly dangerous") | Parked | The danger is the one in docs/essays/supervised-and-self-supervised-development.md: without labels, a program can agree with itself and still be wrong, and nothing shows it. So the design keeps the labels but hides all of them: a problem with a known test suite (a TOML or YAML writer and reader first, where round trips are a strong check), the agents see only self-derived checks (round trips, properties, metamorphic relations, differential testing between two teams on different models; written by a team the builders can't overrule), and the whole official suite is held out and only scored. It measures how far self-supervision gets and where it fails, which is what any real project without a test suite needs to know. Usual guards: protected checks, a budget cap, a sandbox without network. Pairs with "Many generators, compared". Trigger: after jq, YAML 1.2 and HTML5 (the user's order) |
