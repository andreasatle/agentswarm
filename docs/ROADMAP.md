# Roadmap: from mechanisms to a swarm that finishes real problems

Written 2026-10-07, after the user asked how to move forward without stagnating. Order matters: competitiveness can only be studied once the framework behaves well, or the measurements say nothing. Each stage has an exit criterion; the next stage starts when it is met.

## What similar projects teach

- **The closest success is a swarm on a shared repository.** Anthropic's C compiler: 16 Claude agents, no orchestrator and no messages, coordinating only through git and lock files in `current_tasks/` (a blackboard by another name), built a 100,000-line C compiler that compiles Linux, over about 2,000 sessions and $20,000. What made it work: **a near-perfect external verifier** (established compiler test suites; "a loose verifier makes agents solve the wrong problem"), **failing tests as the unit of work** (with hundreds of independent failures each agent took a different one; when all hit the same bug, parallelism collapsed until an oracle split the work), **a regression ratchet** (CI blocking commits that break passing tests, added when fixes kept breaking old features), **short, greppable test output and progress files**, and **specialised roles added later** (deduplication, performance, design critique, documentation). ([Carlini, Anthropic 2026](https://anthropic.com/engineering/building-c-compiler))
- **Long-running builds need a separate evaluator and an explicit definition of done.** A planner expands the goal into a spec; generator and evaluator agree on testable criteria per sprint before building; a separate, tuned evaluator stops premature "done" (self-evaluation praised mediocre work; the evaluator itself had to be tuned by reading its logs). Structure was simplified again as models improved. ([Anthropic, harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps); [Anthropic, effective harnesses for long-running agents](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents): a feature list with a pass flag per feature, one feature per session, a progress file, a ratchet against editing tests)
- **Multi-agent failures are mostly organisational.** In MetaGPT, ChatDev and five other frameworks, failures come from specification and system design, misalignment between agents, and weak verification; requirements get diluted as they pass between agents, and the fix is to give every agent the original requirements. ([MAST, Cemri et al. 2025](https://arxiv.org/abs/2503.13657); [E2EDev 2025](https://arxiv.org/pdf/2510.14509)) Our fifo failure was exactly that: children saw only the planner's child tasks.
- **Blackboards for LLM agents are being revisited** and match or beat orchestrated designs on reasoning and data-discovery tasks; agents decide themselves whether they can contribute. ([Han and Zhang 2025](https://arxiv.org/html/2507.01701v1); [Google/UMass 2025](https://arxiv.org/abs/2510.01285)) No published evaluation on building software yet: AgentSwarm can be one.
- **Multi-agent costs about 15x the tokens** of a chat, worth it where the outcome's value is high, and weakest on tightly interdependent work such as coding. ([Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system))

What AgentSwarm already has from this list: a blackboard with claims (the lock files), git worktrees, independent acceptance tests the producer can't change, typed calls, spend tracking. What it lacks: **a real problem with an external verifier, failing tests as the unit of work, a regression ratchet on the level, the original goal given to every agent, and progress as a number.** Two days went into mechanisms tested on toy tasks; that is the stagnation to stop.

## Stage 1: one real problem, end to end (done: 100%, 2026-10-12)

**The problem:** a CommonMark (Markdown to HTML) converter in pure Python, from an empty seed, judged by the official spec's 652 examples. A held-out fifth of the examples is never shown to any agent, to tell real progress from fitting the visible ones.

**The loop, minimal:** the goal and the spec are on the board; work items are failing spec sections (the verifier decides the split, not a model guessing); builders claim an item, make its examples pass, and the gate merges only if no previously passing example breaks (the ratchet). Every agent sees the original goal next to its item. Progress is the pass rate, visible and logged per merge.

**Teams:** a planner that groups failing examples into items, builders, the gate. Acceptance tests are the spec examples themselves, which no agent writes.

**Cost control:** a first run capped at $5 to measure throughput (examples gained per dollar), then a budget proposal based on that number.

**Exit criterion:** unattended runs raise the pass rate steadily, without the ratchet ever being broken and without stalling; a clear picture of where it stops.

## Stage 2: several teams with different focus

Roles added one at a time, each kept only if it measurably helps: red teams on merged code (bugs found that the spec examples miss, checked against the held-out examples), a refactoring and deduplication team (code size and complexity over time), a reviewer of design, documentation. The C compiler added these after the core loop worked; so do we.

**Exit criterion:** each kept team has a measured contribution; the project reaches its finish line (a high pass rate, held-out examples included).

## Stage 3: dynamics

Models per role (routing, already built), local and hosted models, concurrency, cost per example gained. A second real problem of a different kind (for example a TOML parser, or a document project) to check that the stage 1-2 lessons generalise.

**Exit criterion:** the same framework finishes two different real problems, with per-role model choices backed by data.

## Stage 4: when is a swarm competitive?

The research question, studied once the framework behaves well: against a single big model given the same goal and the same verifier, at problem sizes from small to large, measuring solved share, cost and time. The user's expectation, to test: past some size, no model does it in one step, and a well-behaved swarm wins.

**The model axis (the user, 2026-10-07): one family, many sizes.** Qwen offers dense models from under 1B to 32B and mixture-of-experts models (for example 30B-A3B, 235B-A22B, Coder 480B-A35B), open weights, local and hosted. Within one family, size is the only variable, without differences in training data or style between providers; MoE adds a second axis, total parameters (knowledge) against active parameters per token (compute and cost), so the study can ask which of the two a swarm needs. The stage 3 probes start with the Qwen models this study will use.

## What changes now

- Inventory-suite experiments, routing probes and baseline comparisons pause; their results stay recorded (phase-8-goldilocks.md) and feed stage 3. No paid comparison runs: the router learns which model to use during real work (COLLABORATION.md, rule 6).
- CommonMark is done: 100% of the visible and the held-out examples (2026-10-12).
- Stage 3 starts with the second problem, TOML (`examples/toml/project.yaml`): the same framework, set up with a config, a seed and nothing else.
- TOML is done too (100%, 2026-10-11). Harder problems next, in the user's order (2026-10-12): **jq** (an interpreter for a language, not a format), then **YAML 1.2** (the official yaml-test-suite), then **HTML5 parsing** (html5lib-tests). Each is set up the same way: an importer from the project's own tests, every fifth case held out, checked first against a reference implementation.

## Progress

**Stage 1, built (2026-10-07):** the ratchet check (`checks.<name>.ratchet: <level>`; `gating/ratchet.py`, `checks.RatchetCheck`): more of the level's failing tests pass and none that passed breaks, judged on the merge base, with tests the producer added not counting; the worklist (`worklist:` in a project; `control/worklist.py`): each test file with failing tests on the first shared level becomes an item, `max_open` at a time, `attempts_per_file` each; executors get a `run_tests` tool to see why single tests fail; `agentswarm import-commonmark` writes the seed (a stub `mdconv.to_html`, one protected test file per spec section) and the held-out fifth; `agentswarm score` gives the pass rate of the level, held-out tests included. The project is `examples/commonmark/project.yaml`: Haiku builds, the ratchet gates, a $5 daily budget for the first run. Waiting for: the spec's examples (spec.json from spec.commonmark.org), to be downloaded with the user's permission.

**Stage 1, first run (2026-10-07), stopped at $3 of $5.** Haiku's first item (paragraphs) produced a converter passing 150 of 522 visible examples, but the framework threw it away three times: each attempt broke one example the empty stub passed only because its expected output is empty, the ratchet rejected the change, and the next item started over. A thematic-breaks item fixed one of three examples and was parked because the model called it incomplete. Fixes: executors **repair instead of restart** (`repairs: N`: failing checks keep the work and the model is told what broke) and accept **partial progress** (`partial: true`: passing work is committed and the ratchet judges it). Cost per item: $0.40-0.75, 2-4 million input tokens, mostly cached.

**Stage 1, second run (2026-10-07): the loop works.** From 1 to **162 of 522 visible examples (31%)** in two merged items, and **44 of 130 held-out examples (34%)**: the converter generalises, it doesn't fit the visible examples. $2.93 (the budget is checked between actions, so the last item overshot the $2 limit by $0.93; the two runs together cost $5.93 against a $5 cap). The first item still failed: Haiku again broke the one empty-output example (ex207) and two repair rounds didn't fix it; the second item succeeded. About $0.02 per example gained so far; later sections are harder, so this won't stay linear.

**Stage 1, third run (2026-10-08), Haiku:** from 31% to **40% of visible (209/522) and 43% of held-out (56/130)** examples for about $6.30: 47 more examples at $0.13 each, six times the first run's rate, as the sections get harder. **Qwen's first item, and a provider failure (2026-10-08).** Qwen3-Coder ran one item through OpenRouter, then the OpenRouter credit ran out (HTTP 402). The swarm counted that as builder failures: the worklist created ten items in a minute, each failing at once and spending its section's tries. Fixed: a provider refusal or outage (`ProviderUnavailable`: 401-403, 408, 429, 5xx, lost connections) pauses the project with the reason instead (`Paused`; `agentswarm resume` lifts it), counts against no model, and the worklist adds nothing while paused. The two expensive records just before ($0.88, $0.95) were Haiku's last calls from the stopped run, priced at Haiku's rates; Qwen's one completed call cost $0.097 for 560,000 input tokens. OpenRouter refuses a request when the remaining credit can't cover its worst case (the prompt plus the full output limit), so a small balance stops a large-context builder early. Qwen hasn't been tested as a builder yet.

**Measuring a builder's tokens (2026-10-08), Qwen3-Coder from 40%: +5 examples for $3.25.** The tool traces (`ToolsUsed`, and model calls and the largest prompt per run) show where the tokens go: loops, not work. One run called `list_files` 80 times in a row; others ran the same tests 74-98 times; about half the runs spent all 80 steps and wrote about 1,000 tokens. Every change rewrote the whole 29 KB converter (32 rewrites, 719,000 characters sent in one run), test runs returned up to 297,000 characters, and prompts grew to 188,000 tokens. Haiku did far better in the same loop (+47 for $6.30). Fixes, from SWE-agent's agent-computer interface and Claude Code's editing tools: loop detection, edit by replacement, partial reads and search, short test output, a lower step cap; then the same measurement again.

**Three builders, same start, new tools (2026-10-08).** From the 40% converter, 10 rounds each, with the new tools (partial reads, search, edit by replacement, loop guard, short test output, 40 steps): **Qwen3-Coder +17 visible / +3 held-out examples for $1.18 ($0.07 per example)**; Haiku +7 / +1 for $4.09 ($0.58); Qwen3.6-Plus +1 for $0.56, but 8 of its 10 items ended with an empty reply instead of the typed answer (a format mismatch through OpenRouter, not a skill result). **Spend is now what was charged (2026-10-08).** OpenRouter reported $10.15 used where our records said $6.81: it routes each request to one of several hosts, some dearer than the listed price we estimated with (a test request went to Venice at $0.35/$1.50 per million instead of $0.30/$1.00). **The hard sections (2026-10-08): it's the structure, not the model.** From 43%, Qwen3-Coder gained nothing in 18 items ($3.72). **The planned restructuring, continued (2026-10-08/09).** With room to think, DeepSeek V4 Pro merged 3 of 5 planned steps without regressions (the new modules exist); Haiku 5.5 merged 1, reporting the rest honestly as incomplete ($1.85 for both). Splitting made progress where one item made none, but the last step, switching the whole converter to the new pipeline at once, fixed 16 and broke 54. So the switch-over goes one block type at a time, with the planner allowed a second level and routed builders (Haiku 5.5, Qwen3-Coder, DeepSeek). Its first run ($4.50, nothing merged) exposed a framework bug: children of a split waited for their earlier siblings, but grandchildren didn't wait for their parent's turn, so later sub-steps started on code that wasn't ready; and a sibling that was itself split never counted as done. Fixed (`waits_for` inherits the parent's wait; a split sibling is done when promoted as a whole). The router's outcomes are recorded at the end of each project round, so a run stopped mid-round records them when next opened (14 here).

**The switch-over, second run ($2.32, nothing merged; OpenRouter credit ran out again).** With the order fixed, the traces show the real obstacle: builders read without editing. DeepSeek read files 34-67 times and searched 10-12 times per attempt, used all 60 calls, made no edit and claimed it had; Qwen and Haiku 5.5 did the same on these tasks. On a parser of 1,000+ lines over five files, orientation eats the whole budget. Two proven remedies, built: a repository map in the builder's first message (Aider's repo map: each file's size, and its functions and classes with their lines; `workspace/repomap.py`), and every tool result says about how many calls are left, with a nudge to make the edits and finish when five or fewer remain.

**The restructuring is done: 43% to 89% (2026-10-10/11, $13.92).** The planned switch-over (19 steps, one block type at a time) finished, the old code path is deleted, and the converter passes 464 of 522 visible examples (89%) and 116 of 130 held out (89%). Most steps were merged by GPT-6.1 Sol (about $0.10-0.47 each), some by Sonnet 5.5; Haiku 5.5 and the local gemma4:26b merged almost nothing on these steps, and the router has recorded it. What made it work, all built in these two days after a best-practice review (docs/design/best-practice-review.md): routing by expected cost per success instead of a hand-written order; a cascade that picks again among the models not yet failed on a step; a step every model failed split by the planner (ADaPT), which finished the final switch; a ratchet that protects only the independent acceptance tests, after a 99% version of the final switch was rejected for 7 transitional tests its builder could neither let fail nor delete; passing but unfinished work kept for the next attempt; every run scored, with its cost per example gained (from about $0.07 to $0.01). **YAML 1.2, the fourth problem: set up (2026-10-12).** A YAML 1.2 parser in pure Python from a stub (`examples/yaml/project.yaml`, seed from `agentswarm import-yaml`), judged by the official yaml-test-suite (data-2022-01-17): 402 cases, each giving a test of its parser events, one of its values where JSON holds them, or one that it is rejected; 563 tests visible in 29 files, 118 held out. The jq lesson is in the config as one instruction (hidden tests check what the visible ones don't, so implement each rule as the spec states it), the simplest step before any new machinery; the held-out gap will show whether it is enough.

**jq: 100% visible, 87% held out, the first gap (2026-10-12, $4.14).** One run, 28 work items, every one merged by GPT-6.1 Sol on its first attempt; 2,257 lines in 15 modules (lexer, parser, evaluator, paths, assignment, builtins and more). Visible tests 5/550 to 550/550; held out 2/125 to 109/125. No hard-coded answers in the code. The 16 held-out failures: 9 are builtins or variants no visible test calls (cos, arrays, booleans, nth/1, debug, strflocaltime, split with flags, unpadded base64, abs on a non-number), 7 are edge cases (NaN as an index, slice assignment, an error's wording, numbers kept as written, and similar). So the builders implemented what the tests demanded and no more: overfitting by coverage, not by special cases. The manual documents every missing function, but nothing made a builder read it for completeness. The 87% stands as jq's result: fixing these from what the held-out tests showed would make them training data. The lesson is for the framework, on the next problems: a work item from the spec as well as from the tests (every documented function exists), a self-derived check in the sense of docs/essays/.
